# Deployment

Two environments, each a web app, an API and a database:

| | Web app | API | Database | Deployed when |
|---|---|---|---|---|
| **dev** | Vercel (fixed preview alias) | Render `desk-api-dev` | Neon branch `dev` | every push to `develop`, after CI passes |
| **production** | Vercel (production) | Render `desk-api` | Neon branch `main` | every push to `main`, after CI passes **and a reviewer approves** |

The browser only talks to the web app's domain: Vercel forwards `/api/*` to the environment's API
(`frontend/vercel.json`), as nginx does locally. The refresh cookie stays first-party, and no CORS is needed.

## How a change reaches production

1. A pull request into `develop` runs CI. Nothing merges unless it passes.
2. The merge pushes to `develop`. CI runs again, and its last job, **Deploy to dev**, deploys the API (Render deploy
   hook; migrations run as the container starts), then builds and uploads the web app, then smoke-tests the result.
3. A release pull request `develop → main`, merged when dev looks right.
4. CI runs on `main`. **Deploy to production** waits for approval in the `production` environment, then does the
   same as step 2.

The deploy logic is `.github/workflows/deploy.yml`, called from the end of `.github/workflows/ci.yml`. Render and
Vercel never deploy on their own: Render's auto-deploy is off (`render.yaml`), and Vercel's Git deployments are
disabled (`frontend/vercel.json`), so nothing reaches an environment without passing CI.

## Scheduled work

`.github/workflows/scheduler.yml` runs `send_reminders` against each environment every 15 minutes. It sends the email
outbox, delivery reminders, escalations and deadline warnings. Locally the compose `scheduler` service does this
every minute. Without SMTP settings, deployed environments **discard emails**, because the repository's Actions logs
are public. In-app notifications work either way.

## Configuration

Everything comes from environment variables, and secrets never go in the repository.

**Render** (`render.yaml`; values marked *you* are entered when the blueprint is created):

| Variable | dev | production |
|---|---|---|
| `DATABASE_URL` (*you*) | Neon `dev` branch, direct (not pooled) | Neon `main` branch, direct (not pooled) |
| `FRONTEND_URL` (*you*) | dev web URL | production web URL |
| `DJANGO_SECRET_KEY`, `JWT_SIGNING_KEY` | generated by Render | generated by Render (different) |
| `SEED_DEMO_DATA` | `true` (demo accounts, public passwords) | `false` |
| `API_DOCS_ENABLED` | `true` (Swagger at `/api/docs/`) | `false` |
| `SENTRY_DSN` (optional) | add in the dashboard | add in the dashboard |

**GitHub**: Settings → Environments.

| Environment | Secrets | Variables | Protection |
|---|---|---|---|
| `dev` | `RENDER_DEPLOY_HOOK` | `API_URL`, `WEB_URL` | none |
| `production` | `RENDER_DEPLOY_HOOK` | `API_URL`, `WEB_URL` | required reviewer |
| `dev-scheduler`, `production-scheduler` | `DATABASE_URL`, and optionally `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `SENTRY_DSN` | `WEB_URL` | none |

Repository-wide: secret `VERCEL_TOKEN`, and variables `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID`.

## Setting it up from scratch

1. **Neon:** create project `dataset-request-desk` (Postgres 16, Frankfurt), then a branch `dev` from `main`.
   Copy each branch's connection string with *connection pooling off*.
2. **Render:** New → Blueprint → this repository. Enter `DATABASE_URL` and `FRONTEND_URL` for both services. Then,
   in each service, Settings → Deploy Hook → copy the URL.
3. **Vercel:** create a project from this repository with root directory `frontend` (its Git deployments stay off).
   Create an access token (Account → Tokens). The org and project ids are in Project → Settings → General.
4. **GitHub:** create the environments and values above. On `production`, add yourself as a required reviewer.
5. **First admin in production:** demo accounts are never seeded there. Create one admin once, from a machine with
   Docker, using the production `DATABASE_URL`:
   ```bash
   docker compose run --rm --no-deps -e DATABASE_URL='<production url>' -e RUN_MIGRATIONS=false \
     -e SEED_DEMO_DATA=false api python manage.py createsuperuser
   ```
6. **Uptime monitor:** UptimeRobot (free) checks the production API's `/health` every 5 minutes and emails on failure.
   This also keeps the free instance awake.

## Known limits of the free plans

- **Cold starts:** a Render free instance sleeps after 15 minutes without traffic, and the first request then takes
  about a minute. The uptime monitor keeps production awake; dev may sleep.
- **Upload size:** Vercel's proxy may cap request bodies below the API's 20 MB import limit. Very large exports can
  be imported with `manage.py import_episodes` against the environment's database.
- **Scheduler timing:** GitHub may start scheduled runs a few minutes late, so reminders can arrive up to about
  20 minutes after they fall due.
